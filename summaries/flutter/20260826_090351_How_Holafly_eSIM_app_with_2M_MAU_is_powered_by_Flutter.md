# How Holafly eSIM app with 2M MAU is powered by Flutter

- **컨퍼런스**: Flutter
- **출처**: https://www.youtube.com/watch?v=Y2D6mFHfohI
- **요약 일시**: 2026-08-26 09:03:51

---

## 🔑 핵심 요약
- **Holafly**(eSIM 서비스, iOS/Android/Web 합계 **MAU 200만**, 누적 eSIM 다운로드 **2,500만+**)가 네이티브 앱을 **Flutter로 전면 재작성**한 사례
- 기존 **네이티브 Android/iOS 2개 코드베이스 + 2개 팀**의 기능 지연·플랫폼 간 불일치 문제를 해결하기 위해 크로스플랫폼 전환
- "네이티브 앱을 그대로 클론한다"는 **급진적 접근**으로 **3개월 만에** 재작성 완료 후 신버전 릴리스

---

## 📣 주요 발표 내용
- **전환 배경**: 코드베이스 2개 → 팀이 각각 고립되어 작업 → 기능 배포 속도 저하, 플랫폼별 동작 불일치
- **전환 전략**: 점진적 마이그레이션이 아닌 **기존 앱 전체 클론(full rewrite)** 방식 채택 → 3개월 소요
- **앱 주요 기능**
  - eSIM 간편 설치
  - **실시간 데이터 사용량 관리**
  - **다중 eSIM 관리** (여러 국가를 이동하는 여행자용)
- **네이티브 연동**: eSIM 관리처럼 OS별 API가 다른 영역은 **플랫폼별 standalone 패키지**로 분리
  - 메인 Flutter 앱 개발자는 내부 구현을 몰라도 **단일 Dart 메서드 호출**만으로 사용
- **모노레포 + 모듈화 구조**: Flutter 앱 + 기능별 패키지로 분리, 향후 사내 다른 앱에서 **재사용** 가능하도록 설계
- **글로벌 팀 협업**: 우루과이·아르헨티나·이탈리아·스페인·독일 등 분산 팀이 **하나의 코드베이스**에서 함께 작업
- **로컬라이제이션 파이프라인 개선**: Flutter **`ARB` 포맷**을 활용해 **LLM 자동 번역** 도입 → 더 빠르고 오류 적은 번역 프로세스

## 💡 개발자 포인트
- **네이티브 접근성은 잃지 않는다**: Flutter를 써도 **underlying native platform에 대한 접근은 항상 유지**된다는 점이 핵심 선택 이유
  > OS별 API 차이(eSIM 프로비저닝 등)는 플랫폼 채널 기반 **독립 패키지로 캡슐화**하고, 앱 레이어에는 단일 Dart API만 노출하는 패턴이 실전에서 검증됨

- **패키지 경계 = 문서**: 팀원은 패키지의 **public interface만 보고** 사용법을 파악, 내부 구현을 읽을 필요 없음
  > 분산·다국적 팀에서 온보딩 비용을 줄이는 실질적 장치. 모듈화의 목적이 "재사용"만이 아니라 **인지 부하 감소**에 있다는 점에 주목

- **`ARB`는 LLM 번역과 궁합이 좋다**: `description`, `placeholders`(파라미터), 예시를 명시할 수 있어 **LLM에 컨텍스트를 함께 전달** 가능
  > 단순 key-value가 아니라 **메타데이터를 담을 수 있는 포맷**이라 자동 번역 품질이 올라감. 로컬라이제이션 자동화를 검토한다면 `ARB` 스키마의 `description` 필드를 반드시 채울 것

- **재작성 리스크 판단**: MAU 200만 규모 프로덕션 앱도 **3개월 클론 재작성**이 가능했다는 실증 사례 — 단, "기존 앱 스펙이 이미 확정되어 있다"는 조건이 속도의 전제
