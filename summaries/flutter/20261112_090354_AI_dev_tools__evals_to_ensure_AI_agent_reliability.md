## 🔑 핵심 요약
- Dart·Flutter 개발자 경험(DX) 팀이 **에이전트 기반 개발** 시대에 맞춰 **MCP 서버**, **스킬(skills)**, **에이전트 플러그인**을 제공하는 방향을 설명
- 철학은 기존 도구를 AI로 **대체하는 것이 아니라**, `flutter analyze`·VM 서비스 같은 **결정론적 도구**를 에이전트도 쓸 수 있게 만드는 것 (에이전트도 도구의 "사용자"로 봄)
- 새 에이전트 도구는 **평가(evals)** 로 효과를 검증하며, 기준은 **결과·품질·개발자 경험** 세 가지

## 📣 주요 발표 내용
- **비유로 본 구성 요소** (레스토랑 주방)
  - **MCP** = 주방 설비·재료 (필요한 기능에 접근하는 수단)
  - **스킬** = 레시피 (작업을 수행하는 절차)
  - **규칙(rules)** = 위생·안전 규정 같은 가이드라인
  - **커스텀 에이전트** = 전문 셰프 (예: 접근성 전담 에이전트)
  - **hooks** 등 새 메커니즘도 계속 추가되는 중
- **Dart/Flutter MCP 서버가 제공하는 기능**
  - 내부 루프: 코드 수정 후 **Dart 분석 자동 실행** → 컴파일 오류·경고·린트 위반 확인
  - 실행 중인 앱에 연결해 **핫 리로드 / 핫 리스타트** 수행
  - **런타임 오류 포착**, **위젯 트리** 조회로 레이아웃 문제 수정
  - **pub 도구**: 에이전트가 `dart pub add` / `flutter pub add`를 써서 **잘못되거나 오래된 패키지 버전**을 넣지 않게 함
  - **pub 캐시 읽기 전용 접근**: 캐시 전체 권한 없이도 의존성 소스를 참고할 수 있음
  - **VM 서비스 연동**: 타임라인 추적, 성능 프로필, 힙 스냅샷, 네트워크 프로파일링 정보 조회
- **공식 스킬**
  - 초기 셋업용: **현지화(l10n)**, **라우팅**, 새 앱 시작·정리 시 **아키텍처 모범 사례**
  - 반복 작업용: **통합 테스트 추가**, **위젯 테스트 추가**, **레이아웃 문제 수정**
- **에이전트 플러그인** + 공식 웹사이트 문서로 Flutter AI 개발 환경을 쉽게 설정할 수 있는 경로 제공
- 계층적·모듈화된 구조와 **오픈 프로토콜** 기반으로 만들어 여러 에이전트 환경에서 쓸 수 있게 설계

## 💡 개발자 포인트
- 에이전트에게 "Flutter 앱 만들어 줘"라고만 하지 말고, **공식 Dart/Flutter 스킬 사용**, `dart fix`·정적 분석 수행, 접근성 고려 등 **구체적인 지시**를 줘야 결과가 좋아짐
- 패키지 추가는 에이전트가 `pubspec.yaml`을 직접 고치게 하기보다 **MCP pub 도구**(`dart pub add`)를 쓰게 하는 편이 안전함
> ⚠️ 에이전트에게 pub 캐시 **전체 접근 권한**을 주는 것은 위험함 → MCP의 **읽기 전용** 도구 사용 권장
- 정적 분석만으로는 모든 오류를 잡지 못함 → 동적 레이아웃이 많은 Flutter에서는 MCP로 **런타임 오류·위젯 트리**를 에이전트에게 넘겨주는 게 중요함
- 에이전트가 즉석에서 MCP 서버를 직접 만드는 시도는 실제로 **제대로 작동한 적이 없었음** → 공식 도구를 쓸 것
- **도구 개발 원칙**: 수동 평가로 에이전트가 **실제로 못 하는 작업**인지 먼저 확인한 뒤 만듦 (이미 잘하는 일에 도구를 더하면 도구 공간·컨텍스트 낭비)
- **Evals 설계 기준**
  - **결과**: 버그 수정, 접근성, 현지화 등 요청한 목표를 달성했는가
  - **품질**: 관용적인 Dart 코드인지, 위젯을 적절히 썼는지
  - **개발자 경험**: 오류 복구 루프에 빠지지 않았는지, 스킬·MCP가 올바른 도구로 바로 안내했는지
> 💬 eval 점수 자체가 목표가 아님. 점수가 너무 높으면 **채점 기준이 너무 느슨할** 수 있음. 의사결정에 쓸 수 있는 실제 데이터를 주는 프레임워크를 만드는 것이 목표
