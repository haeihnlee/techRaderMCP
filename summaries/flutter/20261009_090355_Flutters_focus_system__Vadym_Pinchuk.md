## 🔑 핵심 요약
- Flutter **포커스 시스템**은 웹·데스크톱 전용이 아님. **TV 리모컨·보조 기술(Assistive Tech)도 결국 "키보드"**라서 모든 플랫폼에 해당함
- 기본 포커스 관리자(`FocusManager`)는 **기하학적 읽기 순서**만 따르기 때문에, 복잡한 앱에서는 개발자가 `FocusScope`, `FocusTraversalGroup`으로 구조를 직접 알려줘야 함
- 포커스·접근성 개선은 유닛/위젯 테스트도 필요하지만, **보조 기술을 실제로 쓰는 사용자의 테스트**가 가장 중요함

## 📣 주요 발표 내용
- **잘못 알려진 점**: "포커스 시스템은 웹/데스크톱에서 키보드 쓸 때만 필요하다" → 틀림
  - **리모컨 = 키보드**, **보조 기술 = 키보드** 입력과 같은 방식으로 동작
- **기본 동작**: Flutter는 기본적으로 뷰포트 안의 위젯을 **일반적인 읽기 순서(기하학적 위치)**로 정렬해서 탐색함
  - 앱이 조금만 복잡해져도 사용자에게 부족한 경우가 많음
- **개발자가 추가할 위젯**
  - `FocusScope`: 포커스를 **특정 그룹 안에 묶어둠**
  - `FocusTraversalGroup`: 그룹 안에서 **포커스가 이동하는 규칙**을 정함
  - 포커스 관리자가 "어떤 그룹이 있고, 각각 어디에 있는지" 알 수 있는 정보는 사실상 이 위젯들뿐임
- **예시: 체스판**: Tab으로 내 말만 골라서 이동하고 싶으면 상대 말이 사이사이에 있어서 기하학적 순서가 깨짐 → 평면화된 기본 정렬로는 처리할 수 없고 커스텀 탐색 규칙이 필요함
- **시맨틱스(`Semantics`)**: 접근성을 높이는 요소 중 하나. 개발자가 직접 써야 하는데, 장애가 없는 개발자는 어떤 시맨틱스가 필요한지 예상하기 어려움
- 접근성은 포커스만의 문제가 아님. **글꼴 크기, 색상** 등도 함께 고려해야 함

## 💡 개발자 포인트
> ⚠️ **기본 `FocusManager`만으로는 보조 기술과 완전히 호환되지 않음.** 화면 구조에 맞게 `FocusScope` / `FocusTraversalGroup`을 직접 배치해야 함

- **TV·리모컨 앱**(webOS, Android TV 등)에서는 포커스 설계가 핵심임. 영역(행, 패널, 팝업)마다 `FocusTraversalGroup`으로 나누고, 모달이나 팝업은 `FocusScope`로 포커스를 가두는 것을 권장
- 그리드처럼 위치 순서와 논리 순서가 다른 레이아웃은 **커스텀 traversal policy**를 고려할 것 (예: `OrderedTraversalPolicy`, `FocusTraversalOrder`)
- **테스트 전략**
  - 포커스는 결국 위젯이므로 **유닛 테스트·위젯 테스트**로 포커스 이동을 검증
  - 시맨틱스 기반으로 앱 전체를 점검해 주는 접근성 패키지 활용
  - 보조 기술을 실제로 쓰는 **사용자 테스트**는 반드시 해야 함. 개발자가 스크린리더를 켜서 살펴보는 것만으로는 부족함
> 💬 "앱이 사용자 요구를 충족하지 못하는 경우가 거의 99%" — 장애가 있는 사용자 입장에서 생각하기 전에는 앱이 얼마나 정교해야 하는지 알기 어려움
