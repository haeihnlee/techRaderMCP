# API Keys vs. Service Accounts vs. OAuth: How do you pick the right credential on Google Cloud?

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=PDVekoXIAfw
- **요약 일시**: 2026-11-25 09:03:58

---

## 🔑 핵심 요약
- Google Cloud 인증 수단은 **API 키**, **서비스 계정**, **OAuth** 세 가지이고, 쓰임새가 다름
- 공개 리소스(지도)에는 **제한을 건 API 키**, 비공개 리소스에 접근하는 백엔드에는 **서비스 계정**, 사용자 개인 데이터(Drive)에는 **OAuth**를 사용
- 인증 수단을 잘못 고르면 프로젝트 전체가 위험해질 수 있음

---

## 📣 주요 발표 내용
- 예시 시나리오: 커피숍 앱 (실시간 지도 + 비공개 Storage 버킷의 회원 사진 + 사용자 Google Drive 리뷰 가져오기)
- **API 키**: 페이지에 들어가는 긴 문자열이며, "번호표"처럼 **어느 프로젝트에 비용을 청구할지**만 Google에 알림. 소유자를 인증하지 않음
- **서비스 계정**: 코드에 주는 "사원증". 이메일 형태의 식별자와 필요한 권한만 골라 담은 권한 세트(예: 버킷 읽기)를 가짐
- **OAuth**: 사용자가 직접 로그인해 '허용'을 눌러서 **자신의 파일에만** 접근 권한을 주는 방식
- OAuth 옵션을 체크하거나 코딩 에이전트에 **Google Cloud MCP 플러그인**을 추가하면 인증을 자동으로 올바르게 설정할 수 있음

## 💡 개발자 포인트
> ⚠️ API 키는 웹 페이지에 포함돼 전송되므로 누구나 개발자 도구로 복사해서 내 프로젝트에 비용을 발생시킬 수 있음. 모니터에 비밀번호를 붙여둔 것과 같음
- API 키에는 반드시 **애플리케이션 제한**(허용 웹사이트)과 **API 제한**(예: Maps API만 허용)을 설정
- API 키로는 **비공개 Cloud Storage 버킷에 접근할 수 없음**. 백엔드에는 서비스 계정을 사용
- `Cloud Run` 배포 시 서비스 계정을 연결하면 Google 클라이언트 라이브러리가 **임시 토큰을 자동으로 가져옴**. 코드나 설정에 키 파일 같은 비밀 정보를 넣을 필요가 없음
- 서비스 계정에는 꼭 필요한 권한만 부여 (**최소 권한 원칙**)
- 사용자 개인 데이터(Google Drive 등)에 접근할 때는 사용자 동의를 받는 OAuth 흐름이 필수

| 사용처 | 인증 수단 | 이유 |
|---|---|---|
| 웹 페이지 지도 표시 | 제한된 API 키 | 공개 리소스, 과금 프로젝트 식별용 |
| Cloud Run → 비공개 Storage 버킷 | 서비스 계정 | 코드 자체의 신원과 최소 권한 |
| 사용자 Drive 파일 가져오기 | OAuth | 사용자 본인의 동의와 권한 위임 |
