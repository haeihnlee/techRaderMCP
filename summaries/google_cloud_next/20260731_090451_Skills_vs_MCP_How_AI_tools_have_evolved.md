# Skills vs MCP: How AI tools have evolved

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=T6PQIPMlj3E
- **요약 일시**: 2026-07-31 09:04:51

---

## 🔑 핵심 요약
- **MCP**(Model Context Protocol)는 LLM을 외부 API·파일시스템과 연결하는 **표준 프로토콜**이지만, 툴이 늘어날수록 **컨텍스트 블로트**(context bloat) 문제가 발생한다
- **Skills**는 MCP의 대체가 아닌 **보완재**로, 80%는 사실상 "재사용 가능한 프롬프트를 담은 마크다운 파일"이다
- Skills의 핵심 강점은 **progressive disclosure** — front matter만 미리 로드하고 본문은 필요할 때 로드해 메모리를 효율적으로 쓴다

---

## 📣 주요 발표 내용

**MCP의 등장과 한계**
- MCP는 LLM이 **외부 세계 전체**(API, 파일시스템)와 대화할 수 있게 만든 표준 프로토콜
- 오늘날 채팅 앱의 **커넥터(connector)** 기능은 대부분 내부적으로 MCP로 동작
- 문제: 툴 정의 하나가 **수백 줄**에 달할 수 있고, 툴 20개를 붙이면 현재 대화와 무관한 컨텍스트가 통째로 쌓인다

**Skills의 3단 구조**

| 계층 | 내용 | 로드 시점 |
| --- | --- | --- |
| **front matter** | 스킬 요약 + "언제 사용하는지" | 에이전트 시작 시 전체 로드 |
| **body** | 사람이 읽는 영어 지시문 | 모델이 필요하다고 판단할 때 |
| **linked files** (선택) | 결정적(deterministic) 실행용 스크립트·CLI 도구 | 필요 시 |

- 에이전트는 기동 시 모든 스킬의 front matter만 읽어 **내부 레지스트리**를 구성
- 스킬은 단순 프롬프트를 넘어 **스크립트**와 **CLI 도구 사용법**까지 포함할 수 있다

---

## 💡 개발자 포인트

- **둘은 상호 배타적이지 않다** — 실무에서는 MCP + Skills를 함께 쓰고, *스킬이 에이전트에게 MCP 툴을 어떻게 쓸지 알려주는* 구조가 흔하다
- MCP는 **압축이 안 된다**: front matter 같은 계층 구조가 없어 컨텍스트·메모리를 더 많이 먹고, **로드 여부를 선택할 수도 없다**

> **주의:** 툴을 무작정 늘리는 MCP 중심 설계는 컨텍스트 관리 난이도를 급격히 높인다. 외부 시스템 연동이 실제로 필요한 경우가 아니라면, 반복 프롬프트는 Skills로 빼는 것이 컨텍스트 효율에 유리하다.

- Skills는 **영어로 작성**되므로 비개발자도 작성·공유가 가능 → 팀 단위 생산성 도구로 쓸 수 있다
- 스킬은 **반복 iterate → 튜닝 → 팀 공유** 워크플로에 적합 (비즈니스 로직 캡처 용도)
- 발표자 표현: *"가장 인기 있는 프로그래밍 언어는 영어"* — 영어로 자기만의 에이전트를 프로그래밍하는 시대
