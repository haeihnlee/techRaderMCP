# Why code is breaking production (Google Engineers Explain)

## 🔑 핵심 요약
- Google Cloud 팟캐스트에서 **Site Reliability Engineering(SRE) 북 2판**의 저자·편집진(Niall Murphy, Jennifer Petoff, Betsy Beyer, Christof, David Huska, Chris Jones)이 개정 내용을 소개
- 핵심 주제는 **의도적 신뢰성(Intentional Reliability)**: 개별 버그를 그때그때 고치는 대응을 넘어, 시스템 신뢰성을 전략적으로 설계하고 관리해야 한다는 것
- **100%는 잘못된 신뢰성 목표**이며, `SLO`와 `Error Budget`으로 사용자 만족과 비용·개발 속도 사이의 균형점을 정해야 함

---

## 📣 주요 발표 내용
- SRE 북 **2판** 출간: 1판에서 정리한 기본기가 업계 표준이 된 것을 바탕으로, 1판 당시에는 없던 더 세분화된 주제를 추가
- **SLO 챕터 전면 재작성**: 처음 접하는 사람도 이해하기 쉽게 다시 씀
- **클라이언트 사이드 텔레메트리·모니터링** 내용 신규 추가: 그동안의 서버 사이드 중심 관측을 넘어서는 시각
- **신뢰성의 가치**를 다루는 파트 추가: 신뢰성의 가치를 어떻게 정의하고 정당화하며, 조직 안에서 위·아래·옆으로 어떻게 전달할지 정리
- AI 확산, 빠른 성장, 하위 인프라의 불안정화로 **신뢰성이 그 어느 때보다 중요**해졌다는 문제의식

---

## 💡 개발자 포인트
- **SLO는 사용자 관점으로 정의**: 서버가 떠 있는지가 아니라 사용자가 실제로 겪고 신경 쓰는 경험을 기준으로 삼아야 함
- **Error Budget = 100% − SLO**: 예를 들어 SLO가 `99.5%`이면 남는 0.5%가 위험한 작업(신기능 배포, 롤아웃 등)에 쓸 수 있는 예산
- 조직이 합의한 SLO가 있으면 이를 기준으로 **알림 시점**과 **개발 속도를 늦추고 신뢰성에 집중할 시점**을 원칙 있게 판단할 수 있음
- 설계 초기에 `99.9%`, `99.99%` 같은 가용성·지연시간 목표를 정해 두면 **목표에 못 미치는 설계**(나중에 고치기 매우 어려움)와 **과잉 설계**(시간·비용 낭비)를 둘 다 피할 수 있음
- 데이터 없이 신뢰성을 논하면 주관적인 판단이 되어 잘못된 결정이나 갈등으로 이어짐. 실시간 SLO 모니터링이 문제 발생과 정상 복구 시점을 객관적으로 보여 줌
- 경영진 설득 방법: "시스템이 안 돌아가면 기능은 의미가 없다"는 기본 논리에서 출발해, 릴리스 지연·장애가 낳는 **매출·구독 손실**과 장애 대응에 들어가는 **엔지니어링 시간 비용**을 수치로 제시
- SLO는 **숫자로 된 공통 언어**라서 팀과 조직의 경계를 넘어 소통하기 좋음

> ⚠️ 100% 목표는 비현실적이라 **번아웃·영웅주의·지속 불가능한 운영**과 걷잡을 수 없는 비용 증가로 이어짐. 현실적인 SLO가 개발자가 무리한 요구에 반박할 근거가 됨

> ℹ️ 원본 자막이 12,000자에서 잘려, 영상 후반부 내용은 이 요약에 들어가지 않았을 수 있음
