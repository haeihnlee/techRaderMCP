# Why everyone is talking about graphs in AI (and when to skip them)

---

## 🔑 핵심 요약
- AI에서 그래프는 두 가지 역할을 함: **워크플로 그래프**(작업 간 관계·실행 순서 제어)와 **데이터 그래프**(정보 간 관계·연결된 맥락 제공)
- 워크플로는 Google **ADK(Agent Development Kit)**로, 데이터 그래프는 **BigQuery Graph** + `GQL`로 구현한 환불 처리 데모로 설명
- 그래프는 구축·유지 비용이 있으므로 **모든 AI 앱에 필요한 것은 아님** — 단계 제어나 다중 레코드 연결 탐색이 필요할 때만 도입

---

## 📣 주요 발표 내용
- **데모 시나리오**: 고객 환불 문의 → 데이터 그래프에서 주문·결제·환불 이력 조회 → 규정상 검토 필요 시 워크플로 **일시 중지(Human-in-the-loop)** → 승인 후 AI가 답변 작성
- **그래프 엔지니어링**: 문제를 단계(**노드**)와 단계 간 연결(**에지**)로 설계하고, 이를 코드로 옮겨 실행 가능한 워크플로로 만드는 작업
- 노드 유형: 기록을 읽거나 규칙을 적용하는 **함수**, 답변을 작성하는 **AI 에이전트**, **사람의 입력을 기다리는 단계**
- 대표 워크플로 패턴
  - **병렬(Parallel)**: 독립 단계 동시 실행 (주문·결제·환불 이력 확인 3개 병렬)
  - **라우팅(Routing)**: 규칙 결과에 따라 다음 경로 선택
  - **부모/자식 에이전트**: 트리 구조 (그래프의 일종)
  - **루프(Loop)**: 이전 단계로 되돌아가기
- **Graph RAG**: 벡터 검색으로 찾은 레코드에서 출발해 **관계(에지)를 따라가며** 추가 맥락을 수집하는 RAG 방식
  - 예: 주문 레코드(트레일 러닝화 $60, 12일 전)만으로는 결제 분쟁 여부·최근 12개월 환불 횟수를 알 수 없음
  - 주문 → 결제(분쟁 없음), 주문 → 고객 → 환불 이력 요약(12개월 내 1건)으로 탐색해 필요한 사실 확보
- **BigQuery Graph**: 기존 BigQuery 테이블 위에 그래프 관계를 정의하고 `GQL`(그래프 쿼리 언어)로 연결된 레코드 조회

## 💡 개발자 포인트
- 에이전트에게 "기다려"라고 프롬프트로 지시하는 것만으로는 실제 대기를 **보장할 수 없음** → 승인 대기 같은 제어는 워크플로 그래프의 명시적 단계로 구현
- 역할 분리: **확인 로직·날짜 처리는 코드**, **답변 작성은 모델**에 맡기기 (ADK로 단계별 적합한 모델 선택 가능)
- 합류(Join) 설계: 환불 규칙 노드는 3개 확인 작업 결과가 **모두 도착해야** 실행되도록 에지 구성
- 그래프에서 "관계가 **일급 개념(first-class)**"이라는 의미: 관계를 직접 정의하고 쿼리가 그 관계를 따라가도록 함
- 테이블 조인이나 일반 RAG로도 같은 사실 조회는 가능 — 그래프는 **여러 연결된 레코드를 거쳐야 답이 나오는** 경우에 특히 유용
- 데모는 병렬성 시연을 위해 3번 개별 읽기를 썼지만, **하나의 통합 쿼리**로도 가능 → 실서비스에선 각 방식의 지연시간·비용 비교 필요

> ⚠️ 트레이드오프
> - 워크플로 그래프는 구축·유지보수 비용이 큼 — 작은 작업은 **함수/도구 몇 개를 가진 단일 에이전트**로 충분
> - 더 많은 연결을 따라갈수록 **시간·비용 증가**, 불필요한 정보가 섞일 수 있음
> - 관련성 선택은 여전히 개발자 몫이며, 모델은 여전히 실수할 수 있음

> 💬 도입 판단 기준: 해결하려는 문제에서 출발해 "어떤 단계가 필요한가 / 어떤 정보가 필요한가 / 조각들이 어떻게 연결되는가"를 먼저 자문할 것
