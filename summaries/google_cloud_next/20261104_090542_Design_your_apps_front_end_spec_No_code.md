# Design your app's front end spec (No code)

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=YNXnbGrXEp4
- **요약 일시**: 2026-11-04 09:05:42

---

## 🔑 핵심 요약
- **Google Antigravity**에서 Gemini 기반 커스텀 에이전트를 만들어, 코드 없이 프론트엔드 **설계 사양서(spec)**를 작성하는 과정을 보여주는 'Build It' 에피소드
- **사양 주도 개발(spec-driven development)**은 엔지니어가 아니어도 쓸 수 있으며, 그냥 감으로 코딩(vibe coding)하는 것보다 결과물 품질이 높음
- 에이전트를 **사고 파트너(thinking partner)**로 두고 반복 대화로 설계를 다듬은 뒤, 별도의 **스크라이브(scribe)** 에이전트가 문서를 작성하도록 역할을 나눔

---

## 📣 주요 발표 내용
- 첫 프롬프트에서 사양서를 바로 만들게 하지 않고, "그 일을 할 **에이전트 + 스킬 조합**을 만들어 달라"고 요청함 (에이전트가 문제를 너무 서둘러 풀려는 경향이 있어서)
- 에이전트 **하네스(harness)** = 시스템 지침(페르소나) + 사용 가능한 도구 + 목표. 이걸 고쳐서 맞춤형 에이전트 경험을 만듦
- 페르소나 설정: 대화형·재미있는 톤, "옆에 앉은 친구에게 개념을 가르치듯" 설명하도록 지시
- 에이전트가 직접 문서를 쓰지 않고, 사용자와 협업해 결론을 낸 뒤 **스크라이브 에이전트**에게 넘기도록 구성
- 컨텍스트 오염을 막으려고 Antigravity **새 세션**에서 "클라이언트 계획 에이전트를 사용하자"라는 말로 에이전트 활성화
- 입력 자료: **Google AI Studio**에서 바이브 코딩한 스마트 피트니스 앱 프로토타입 스크린샷과 기존 데이터 아키텍처 사양
- 최종 산출 사양서 구성:
  - 글로벌 내비게이션 및 뷰 맵
  - 페이지 / 뷰 사양
  - 재사용 컴포넌트 카탈로그
  - 클라이언트 상태 및 데이터 흐름 매트릭스
  - 프론트엔드 테스트 / E2E 테스트 매트릭스
  - 변경 로그 및 감사 추적(audit trail)

---

## 💡 개발자 포인트
- **메인 에이전트 POC → 하위 에이전트/스킬 설계** 순서로 먼저 구조를 잡으면, 바로 결과물을 요청할 때보다 품질이 좋아짐
- **사고(설계 협의) 역할과 기록(문서화) 역할을 나누는** 멀티 에이전트 패턴은 그대로 가져다 쓸 수 있음
- 새 작업은 **새 세션에서 시작**해 이전 컨텍스트와 섞이지 않게 하기
- 라우트(route) → 컴포넌트 계층 구조 → 상태/데이터 흐름 순서로 반복 대화하면서 개념을 하나씩 정리
- 사용자는 자연어와 단순한 논리로만 설명했고, 기술적 세부 사항은 Gemini가 **다른 에이전트가 구현에 바로 쓸 수 있는 사양**으로 바꿔 줌
- 기계적인 반복 작업은 에이전트에게 맡기고, 사람은 **판단·디자인·취향**과 확장성·유지보수성 고민에 집중

> 주의: 에이전트에게 한 번에 결과물(사양서)을 요청하면 너무 서둘러 원하는 수준의 결과가 나오지 않을 수 있음. 먼저 "지금은 만들지 말고 도와 달라"고 의도를 분명히 할 것
