## 🔑 핵심 요약
- 멀티모달 에이전트의 장기 기억은 **사실(Facts)** 과 **이해(Understanding)** 두 종류로 나누어 서로 다른 저장소에 둬야 함
- 사실은 **구조화된 DB(SQL)** 에 넣어 정확히 조회하고, 이해는 **벡터 저장소** 에 넣어 의미로 검색함 (예: `Agent Platform Memory Bank`)
- 원시 지각 데이터(카메라 프레임·오디오)는 에이전트 메모리가 아니며, 거기서 **추출한 의미** 만 기억함

---

## 📣 주요 발표 내용
- **단기 기억 vs 장기 기억**: 세션 중 컨텍스트는 RAM처럼 세션이 끝나면 사라짐. 핵심 설계 질문은 "다음 세션까지 가져갈 가치가 있는 것은 무엇인가?"
- **사실(Structured Memory)**: 일정, 구매 내역, 위시리스트처럼 ID·날짜가 있고 CRUD가 가능한 정확한 데이터 → "찾아보는 것(lookup)"
- **이해(Semantic Memory)**: "심플한 스타일 선호", "추위를 잘 탐", "자신감이 필요할 때 어두운 색" 같은 패턴 → "떠올리는 것(recall)"
- **저장소 선택**
  - 사실: `Postgres`, `MySQL`, `Cloud SQL` 등 스택에 맞는 SQL DB
  - 이해: 벡터 저장소 범주 — `pgvector`, `AlloyDB`, 관리형 옵션인 **Agent Platform Memory Bank**
- **Memory Bank 의 차별점**: 벡터 저장뿐 아니라 과거 세션을 읽어 **유용한 기억을 추출** 하고 **시간에 따라 업데이트** 함 (일반 벡터 저장소라면 추출 로직을 직접 구현해야 함)
- **메모리 루프**: 세션 시작 시 읽기 → 바뀐 내용 쓰기 → 다음 세션에서 불러오기
- **세션 시작(Cold Open)**: DB에서 예정 행사·위시리스트·프로필을 로드하고, 벡터 저장소에서 스타일 선호·착용감 제약·좋아하는 색상을 검색 → "목요일에 저녁 약속이 있으시죠(SQL), 간결한 스타일을 선호하시죠(Semantic)" 처럼 **하나의 답변에 두 메모리 시스템** 을 결합
- **추출 시점**: 대화 도중, 각 턴 종료 후, 특정 간격, 세션 종료 시 중 선택 가능. Memory Bank는 세션 중간 생성 트리거를 직접 지원

## 💡 개발자 포인트
> ⚠️ 흔한 실수: 사실·선호·일정까지 **모든 것을 벡터 저장소에 넣는 것**. 벡터 검색은 유사도 기반이라 정확한 답이 필요한 질문("내가 무엇을 샀지?")에서 추측성 결과를 반환할 위험이 있음
- 질문 유형으로 라우팅: "목요일 일정은?" → DB 쿼리, "나는 보통 저녁 식사로 뭘 좋아하지?" → 시맨틱 검색
- **사실은 즉시·동기식으로 저장**: "블레이저를 위시리스트에 추가해 줘" → 도구 호출(tool call)로 바로 DB write
- **이해는 판단 후 저장**: "오늘은 노란색이 마음에 드네" 한 마디로 장기 선호를 갱신하지 말 것. 사용자가 이유를 설명하거나 여러 세션에 걸쳐 패턴이 반복될 때만 반영해 메모리 노이즈 방지
- 모든 문장을 영구 선호로 처리하지 말고, 메모리 서비스가 대화를 검토해 **보관할 가치가 있는 것만 추출** 하도록 구성
> ⚠️ 실시간 음성 에이전트 주의: 추출은 모델이 대화를 읽고 의미를 추론하는 **무거운 작업** 이라 지연을 유발함. 추출이 오디오 스트림을 막지 않도록 **실시간 경로(hot path)에서 분리** 해 비동기로 실행할 것
- 대화 중 바로 추출하면 짧은 단위로 깔끔한 메모리가 생기고, 사용자가 중간에 이탈해도 내용이 보존되는 장점이 있음
- 권장 2트랙 구조: **사실 = 빠른 동기 write**, **이해 = 느린 비동기 추출** (데모에서는 세션 종료 후 추출)
- 원시 비디오/오디오는 재생·감사·디버깅·학습 데이터용으로 **별도 스토리지** 에 보관할지 따로 결정. 에이전트 메모리에는 "검은 모자를 또 쓰고 있음", "이번 저녁은 격식 있는 자리" 같은 추출된 의미만 저장
- 아키텍처는 특정 제품에 종속되지 않음 — Memory Bank는 하나의 관리형 옵션일 뿐
