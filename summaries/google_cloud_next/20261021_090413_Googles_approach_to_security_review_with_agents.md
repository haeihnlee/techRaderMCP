# Google’s approach to security review with agents

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=czKuoutcwYc
- **요약 일시**: 2026-10-21 09:04:13

---

## 🔑 핵심 요약
- Google 보안 엔지니어 Nick Galloway 팀이 에이전트 기반 보안 리뷰 프로젝트 **Mantis**를 만들어 오픈소스로 공개했습니다. 보안 리뷰용 **skills** 세트와 SDK 기반 오케스트레이션으로 구성됩니다.
- 에이전트에게 "find vulnerabilities in my code"처럼 단순하게 요청하면 **오탐(false positive)이 매우 많습니다**. 그래서 **위협 모델(threat model)을 먼저 만들고**, 단계별 skill로 나눠 분석하는 방식을 씁니다.
- 에이전트를 **페르소나**("보안 엔지니어 에이전트")가 아니라 **아젠다**(지금 하는 구체적 작업: 위협 모델링, 리뷰 비평, 특정 취약점 탐색 등)로 정의하면 **토큰 효율**과 정확도가 모두 좋아집니다.

---

## 📣 주요 발표 내용
- **Mantis의 시작**: 작년 크리스마스 무렵 Gemma 기반 로컬 모델로 Linux 커널 취약점 탐색을 시도했지만 실패했습니다. 이 경험으로 "문제를 에이전트가 감당할 수 있는 크기로 쪼개는 법"을 익혔습니다.
- 이후 강력한 모델(발표에서는 "mythos"라고 언급)이 나오면서 Mantis가 내부 프로젝트로 본격 시작됐습니다. Google 내부 보안 엔지니어 여러 명의 노하우가 skill에 담겨 있습니다.
- **오탐 문제**: 내부 개발자들이 Antigravity로 바로 취약점을 찾게 하면 결과가 20~수백 건 나오지만, 실제 취약점은 **몇 %에 불과**했습니다.
  - 원인 1: 모델이 해당 코드베이스로 학습되지 않았습니다.
  - 원인 2: 코드가 실행되는 맥락을 이해하지 못합니다.
- **해결 방식**: 아키텍처 이해와 위협 모델을 먼저 만들어 **trust boundary**를 파악합니다. 그런 다음 찾은 결과 중 관련 없는 것을 걸러냅니다.
- **Mantis의 두 가지 구성**
  - **Skills 방식**: 도구를 실행하지 않고 에이전트에게 주는 상위 수준 지침입니다. skill 안에 **입출력 계약(input/output contract)**이 정의돼 있습니다. 아키텍처와 위협 모델을 파일로 출력하므로 코드베이스에 바로 커밋할 수 있습니다.
  - **SDK 오케스트레이션 방식**: 위협 모델을 데이터 스토어에 저장해 다른 팀이 함께 쓸 수 있습니다.
- Aaron Edelman은 Mantis의 threat modeling skill을 개인 프레임워크에 맞게 단순화해 쓰는 사례를 시연했습니다.

## 💡 개발자 포인트
- **계획 단계에서 위협 모델링하기**: 새 기능을 계획할 때 스펙(제품 요구사항)을 근거로 위협 모델을 만듭니다.
  - 예: "인증 없는 사용자가 공개 폼에 입력하고, 그 값을 DB에 저장한다" 같은 맥락을 줄수록 위협 모델이 정확해집니다.
- **규모에 따라 저장 방식 고르기**

| 상황 | 권장 방식 |
| --- | --- |
| 1인 개발자 | 레포 안에 위협 모델 **마크다운 artifact**를 두고, 기능을 추가할 때 함께 갱신 |
| 규모가 큰 팀 | 위협 모델을 별도 저장소나 데이터 스토어에서 관리하고, 변경할 때마다 **근거(justification)와 이력** 추적 (Mantis 방식) |

- **위협 모델은 사람이 보완하기**: 위협 모델 생성 자체는 에이전트가 하고 결정적(deterministic) 스크립트는 쓰지 않습니다. 대신 **mitigation**은 사람이 직접 검토합니다. 빠진 항목을 발견하면 위협 모델과 함께 **skill 자체도 수정**해 다음부터 찾게 합니다.
- **TDD에 보안 엣지 케이스 넣기**: 실패하는 테스트를 먼저 쓸 때 happy path뿐 아니라 보안 엣지 케이스도 포함합니다.
  - 예: **RBAC**를 구현한다면 "일반 사용자가 admin 기능에 접근하면 실패해야 한다" 같은 테스트를 기본 작업으로 함께 작성합니다.
- 보안 skill은 하나의 큰 프롬프트로 주지 말고 **작업 단위로 나눠야** 합니다. 그래야 컨텍스트 낭비가 줄고 정확도가 올라갑니다.

> ⚠️ 주의: 사이버보안 특화 모델이 있어도 "보안을 잘하는 모델"만으로는 부족합니다. 보안은 프로젝트·조직마다 다른 **구체적 맥락**의 문제이므로, 위협 모델로 맥락을 줘야 오탐을 줄일 수 있습니다.

> ℹ️ 참고: 원본 자막이 12000자에서 잘려 있어, 이 요약은 영상 앞부분(위협 모델링 → TDD 보안 테스트 단계까지)만 다룹니다.
