## 🔑 핵심 요약
- 라이브 **음성 에이전트**가 실제 브라우저를 제어하는 구조는 **보기 → 생각 → 행동 → 다시 보기** 루프 하나로 요약된다
- 모델은 스크린샷의 **X/Y 좌표**를 지정하고, 브리지가 **Chrome DevTools Protocol(CDP)**로 실제 클릭·타이핑을 수행한다
- 느린 도구는 **백그라운드 실행 후 즉시 반환**하고, 결과 확인은 다음 **스냅샷**으로 대체해 대화 끊김을 막는다
- 되돌릴 수 없는 작업은 **서버 측 확인(액션 토큰)**을 거쳐 사람이 승인하도록 한다

## 📣 주요 발표 내용
- **브라우저 제어 루프**
  - 하나의 **Live 세션 모델**이 음성 입력과 브라우저 상태를 함께 추론
  - 요청 청취 → 화면 확인 → 다음 동작 1개 결정 → 실행 → 재확인
- **좌표 기반 액션**
  - 모델은 버튼 이름이 아닌 스크린샷 상의 **좌표**를 가리킴
  - 작은 브리지가 `CDP` 명령으로 Chrome에 클릭/입력 전달
- **스트리밍 대신 스냅샷**
  - 화면을 연속 스트리밍하면 이미지마다 새 입력 턴처럼 동작해 대화가 끊김
  - 동작 후 페이지가 **안정되면 스크린샷 1장**만 모델에 전달
- **비동기 액션 / 동기 읽기 규칙**
  - 액션(클릭·입력·탐색): 백그라운드 실행, 즉시 반환 → "지금 구글 지도를 엽니다"처럼 말하며 대화 지속
  - 읽기("이 페이지에 어떤 텍스트가 있지?"): 답이 있어야 다음 결정 가능하므로 **동기 실행**
  - **ADK**의 도구 실행 전 **콜백(before-tool callback)** 하나로 규칙 강제 — 도구를 다시 작성할 필요 없이 한 번만 분류
- **안전 장치**
  - 탐색은 자유롭게, **양식 제출·계정 설정 변경** 등 비가역 작업은 멈추고 사용자 확인
- **다음 에피소드 예고**: 세션 종료 후 에이전트의 **장기 기억(long-term memory)**

## 💡 개발자 포인트
- 실시간 음성 UX에서 **침묵은 곧 버그** — 3~4초 걸리는 도구(웹사이트 열기 등)를 동기로 기다리지 말 것
- **"시각 정보가 느린 반환값을 대체한다"** — 성공 여부는 긴 tool response 대신 다음 스냅샷으로 확인
- 도구를 `action`(async) / `read`(sync) 두 범주로 분류하고 ADK 콜백에서 일괄 처리
- 스냅샷 타이밍은 **페이지 안정화 이후**로 맞춰야 잘못된 상태를 보고 추론하는 문제를 줄일 수 있음

> ⚠️ 프로덕션에서는 프롬프트 지시만으로 확인 절차를 맡기지 말 것. **실제 액션 토큰을 사용한 서버 측 검증**이 필요하며, 모델이 유일한 안전장치가 되어서는 안 된다.

> ⚠️ 화면을 연속 영상 스트림으로 Live 세션에 보내면 매 프레임이 입력 턴처럼 처리되어 음성 대화가 끊길 수 있다.
