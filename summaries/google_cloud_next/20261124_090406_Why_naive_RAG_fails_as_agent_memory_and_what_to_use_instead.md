# Why naive RAG fails as agent memory (and what to use instead)

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=gau6i7AJ6jw
- **요약 일시**: 2026-11-24 09:04:06

---

## 🔑 핵심 요약
- 단순 **RAG**를 에이전트 메모리로 쓰면 서로 충돌하는 사실(예: "뉴욕 거주" vs "샌프란시스코로 이사")을 모두 가져와 모델이 혼란을 겪음
- 에이전트 메모리 구현의 3가지 표준 방식(**플랫 프롬프팅 / 일반 RAG / 지식 그래프**)은 각각 컨텍스트 폭발, 상태 통합 부재, 높은 구현 부담이라는 한계가 있음
- **Memory Bank**는 백그라운드에서 비동기로 동작하며 개체 추출·중복 제거·충돌 해결·사실 업데이트를 자동 처리해, 지식 그래프의 구조적 품질과 RAG의 토큰 절감을 함께 제공

---

## 📣 주요 발표 내용
- **플랫 프롬프팅**: 원시 대화 기록을 컨텍스트 윈도우에 그대로 추가하는 방식으로, 구현은 쉽지만 **컨텍스트 폭발** 문제가 생김
- **일반 RAG (벡터 DB)**: 일치하는 텍스트 청크만 가져와 토큰은 절약하지만 **상태 유지형 통합(stateful consolidation)** 기능이 없음
- **오픈 지식 그래프**: 개체·관계를 그래프 DB로 추출해 연관 관계를 추적하는 방식으로, 복잡한 관계 표현에는 강하지만 **개발 부담이 큼**
- **Memory Bank**: 메인 실행 루프를 차단하지 않도록 **비동기 백그라운드**에서 실행됨
- Memory Bank가 자동으로 처리하는 작업: **개체 추출**, **중복 제거**, **충돌 해결**, **사실 업데이트**
- 몇 줄의 코드만으로 에이전트에 장기 메모리를 붙일 수 있음

---

## 💡 개발자 포인트
- 벡터 검색만으로는 "어떤 사실이 최신인가"를 판단할 수 없으므로, 사용자 상태가 바뀌는 도메인(주소, 선호도, 설정 등)에서는 naive RAG 메모리를 피해야 함
> ⚠️ 주의: 일반 RAG는 오래된 사실과 새 사실을 함께 반환하기 때문에, 충돌 해결 로직이 없으면 에이전트 응답 품질이 떨어짐
- 대화 기록을 프롬프트에 계속 누적하는 방식은 토큰 비용과 지연 시간이 선형으로 커지므로 프로토타입 단계에서만 쓰는 것이 좋음
- 메모리 생성·정리는 **비동기**로 분리해 에이전트의 응답 지연에 영향을 주지 않도록 설계하는 것이 핵심 패턴
- 지식 그래프를 직접 구축·운영하기 전에, 추출·통합을 관리형으로 처리해 주는 메모리 서비스를 먼저 검토하면 구현 비용을 줄일 수 있음

| 방식 | 장점 | 한계 |
|---|---|---|
| 플랫 프롬프팅 | 구현이 매우 쉬움 | 컨텍스트 폭발 |
| 일반 RAG (벡터 DB) | 토큰 절약 | 충돌 해결·최신성 판단 불가 |
| 오픈 지식 그래프 | 복잡한 관계 추적 | 개발 부담 큼 |
| Memory Bank | 구조적 품질과 토큰 절감을 함께 제공, 비동기 처리 | (영상에서 언급 없음) |
