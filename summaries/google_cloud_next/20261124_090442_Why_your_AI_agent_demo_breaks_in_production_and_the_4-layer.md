# Why your AI agent demo breaks in production (and the 4-layer fix)

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=BKVDdL1InsA
- **요약 일시**: 2026-11-24 09:04:42

---

## 🔑 핵심 요약
- AI 엔지니어링의 중심이 **프롬프트 엔지니어링에서 루프 엔지니어링으로** 옮겨가고 있으며, 루프는 모델과 애플리케이션 사이의 **하네스(harness)** 계층 안에 있음
- 하네스의 핵심은 "모델 + 도구(CLI·파일시스템·MCP) + `while` 루프"로 단순하지만 취약하므로, 프로덕션에서는 **4계층(학습 → 보호 → 검토 → 점수 매기기)**으로 감싸야 함
- 프롬프트는 조언에 불과하므로 **결정론적 게이트**, **독립된 리뷰어 에이전트**, **하네스 자체 평가(eval)**로 신뢰성을 보장해야 함

---

## 📣 주요 발표 내용
- **1계층 · 학습(컨텍스트 관리)**: 간결한 컨텍스트 맵(`AGENTS.md` 같은 에이전트 파일), 디스크에 두는 **영구 메모리**(마크다운 계획·작업 목록), 필요할 때만 불러오는 **모듈식 스킬**
- **Agent Skills 명세**: 2025년 12월 오픈소스로 공개됐고, Claude Code(자막 표기는 "Cloud Code")·Codex·Antigravity 등 주요 코딩 도구가 지원
- 스킬 구조: 폴더 하나에 `SKILL.md`(맨 위에 사용 시점을 적은 메타데이터, 아래에 마크다운 지침)가 들어가고, 헬퍼 스크립트와 참조 문서는 선택 사항
- **점진적 공개(progressive disclosure)**: 1) 검색 단계에서는 이름·설명만 읽음 → 2) 프롬프트와 맞을 때만 전체 `SKILL.md`를 로드 → 3) 추가 파일·스크립트는 해당 단계에서만 로드
- **에이전트 플러그인**: 여러 스킬, 실시간 MCP 서비스, 라우팅 규칙을 **플러그인 JSON 매니페스트** 하나로 묶어 설치 단위로 배포
- **Google Cloud 개발자 플러그인**: 원클릭 설치, **Developer Knowledge MCP 서버**의 실시간 문서, IAM·결제 보호, **150개 이상의 Google Cloud 스킬** 제공. Antigravity 외의 호환 에이전트에서도 사용 가능
- **2계층 · 보호(결정론적 게이트)**: 컴파일러, 타입 검사기, 고정 입력 테스트, 린트, 시크릿 스캐너, SCA, 규칙 기반 보안 테스트
- **3계층 · 검토**: 생성과 비평을 분리함. 새 컨텍스트 창에서 독립된 리뷰어 에이전트(Gemini)를 돌리고, 헤드리스 브라우저 스크린샷·비디오로 **멀티모달 검토**
- 리뷰 도구 사례: Gemini의 PR 자동 리뷰(일회성)와 **대화형 리뷰**(파일별 한 문장 요약), PR을 인터랙티브 시각화·비디오로 바꾸는 `Repo Walkthrough` 스킬, 화면 크기별 녹화 기반 시각적 QA 자동화, PR 오디오 요약
- **4계층 · 점수 매기기(평가)**: 에이전트 파일 수정, MCP 도구 추가, 모델 업그레이드처럼 **하네스 자체가 바뀔 때** 회귀를 잡는 "진단 테스트 벤치"
- 에이전트 평가 첫 번째 패턴인 **도구 사용 평가**: 올바른 도구를 골랐는지, 올바른 입력(예: 주문 ID)을 넘겼는지, 올바른 순서를 지켰는지(예: 환불 전 자격 확인)를 측정

> 자막이 12,000자에서 잘려서 4계층 평가의 나머지 패턴(총 4개 중 2~4번째)은 요약에 빠져 있음

## 💡 개발자 포인트
- 긴 규칙·문서를 시스템 프롬프트에 넣으면 컨텍스트가 커져서 오히려 코딩 성능이 떨어짐. **스킬로 쪼개서** 필요할 때만 로드할 것
- 워크플로 하나(PR 포맷, DB 마이그레이션 등)면 **스킬 하나로 충분**함. 플러그인은 여러 스킬과 MCP를 함께 묶어야 하는 복잡한 도메인에서만 쓸 것
- 새 테스트는 **구현 전에 먼저 실패하는지 확인**하고, 바로 통과하는 테스트는 제외할 것
- 에이전트가 assertion 변경, skip 태그 추가, 린터 비활성화로 우회하는 것을 막으려면 **Git 훅**을 쓸 것. 기존 테스트 수정, 테스트 수·커버리지 감소, 설정 파일 변경이 있으면 자동으로 실패 처리
- 새 테스트는 여러 번 재실행해서 **flaky 테스트를 차단**할 것(예: 성공률 80%면 차단). 테스트가 스스로 DB 상태를 정리하고 실제 로컬 DB를 대상으로 실행되게 할 것
- 커밋마다 **시크릿 스캔**을 돌리고, 정적 분석으로 SQL 문자열 연결과 검증 없는 입력을 잡을 것
- 의존성은 **lock 파일에 고정**하고 취약점을 검사할 것. **slop squatting**(에이전트가 잘못 짚은 패키지 이름을 노린 악성 패키지) 방지 목적
- 게이트가 실패하면 규칙 ID, 파일, 줄 번호, 실패한 assertion이 담긴 원시 로그를 에이전트에 전달하고, **재시도는 3회까지**만 한 뒤 로그를 붙여 사람에게 넘길 것
- 게이트 설정과 훅 스크립트는 **에이전트 권한 밖에** 두고, 에이전트가 수정하려 하면 빌드를 실패 처리할 것
- 반복되는 게이트 실패 패턴은 리포지토리 스킬 파일에 반영할 것. 다만 **스킬을 업데이트한 뒤에도 게이트는 유지**해야 함. 새 문제는 게이트를 먼저 만들고 그다음 스킬을 고칠 것
- 대형 PR은 먼저 **정말 그 크기가 필요한지** 따져 보고 분할을 검토할 것. 분할이 어려우면 "수박 나눠 먹기"처럼 나눠서 검토
- 앱 유형별 E2E 전략: UI 앱은 브라우저 테스트, CLI는 `tmux` 기반 테스트, 데이터 집약형은 다양한 데이터 유형·볼륨 테스트

> 주의: `AGENTS.md` 수정이나 모델 교체로 특정 작업이 20% 빨라져도 다른 워크플로 10개가 조용히 깨질 수 있음. 하네스를 바꿀 때는 반드시 eval로 확인할 것
