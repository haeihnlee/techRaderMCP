# Harness engineering and context curation

- **출처**: https://www.youtube.com/watch?v=NcHnt6ItJPM
- **요약 일시**: 2026-09-30 09:05:04

---

## 🔑 핵심 요약
- **하니스 엔지니어링(Harness Engineering)**: 모델 주변의 **맥락(context)과 환경**을 설계해, 모델이 실행될 때마다 사용자의 의도를 자연스럽게 파악하도록 만드는 접근
- 모델 성능이 좋아져도 "내가 원하는 것"을 **자동으로 더 잘 알게 되지는 않는다**는 점이 핵심 통찰
- 목표는 **"게으른 프롬프터(lazy prompter)"** 가 되는 것 — 프롬프트 대신 도구·맥락을 미리 갖춰두는 방식

---

## 📣 주요 발표 내용
- 발표자는 작년 5월 이후 **에디터를 거의 열지 않고** 에이전트에게 코드 작성을 맡기고 있다고 언급
- 모델은 프롬프트에 명시된 내용보다 **작업 환경·맥락에서 더 많은 단서**를 얻음
- 모델이 똑똑해지고 지시를 더 잘 따를수록, **"좋은 결과"의 기준(definition of good)** 을 명확히 해줄수록 더 복잡한 작업 수행 가능
- **Context curation**: 모델이 스스로 방향을 잡을 수 있도록 필요한 **도구(tools)와 맥락**을 사전에 큐레이션
- 엔지니어의 역할이 "코드 작성"에서 **"사양·기준·환경 설계"** 로 이동하는 흐름에 대한 논의

---

## 💡 개발자 포인트
- 매번 긴 프롬프트를 쓰기보다 **프로젝트 레벨 컨텍스트**(예: `CLAUDE.md`/`AGENTS.md` 같은 지침 파일, 규칙, 예제)를 정비하는 것이 투자 대비 효과가 큼
- 모델에게 **성공 기준**(테스트, 린트, 검증 스크립트 등)을 환경으로 제공하면 에이전트가 자체 검증하며 작업 가능
- 필요한 **도구(MCP, CLI, 스크립트)** 를 하니스에 연결해 두면 프롬프트에 세부사항을 담을 필요가 줄어듦
- 모델 업그레이드만으로 품질이 오르길 기대하지 말고, **의도 전달 체계**를 지속적으로 개선해야 함

> ⚠️ 운영 배포 코드를 사람이 직접 읽지 않는 방식은 리스크가 있음 — 그만큼 **자동 검증·기준 설정**이 하니스에 반드시 포함되어야 함
