# BigQuery vs. Production SQL: When should you use a data warehouse instead of a relational database?

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=VhMuZFB0cdM
- **요약 일시**: 2026-11-03 09:04:56

---

## 🔑 핵심 요약
- **BigQuery**는 대량 데이터 **분석**용 서버리스 데이터 웨어하우스로, 수천 행이든 수조 행이든 같은 SQL로 몇 초 안에 결과를 돌려준다
- 서버 프로비저닝·확장·패치가 필요 없고, **쿼리한 만큼만 비용**을 낸다
- 소량 데이터 조회나 사용자 한 명을 찾는 것 같은 **단건 조회**는 일반 관계형 DB(Production SQL)가 맡는 게 맞다

---

## 📣 주요 발표 내용
- 스프레드시트는 약 **100만 행**을 넘으면 느려지고 결국 멈춘다
- 관계형 DB를 직접 운영하면 사이징·확장·장애 대응(새벽 3시 서버 다운)을 사람이 직접 맡아야 한다
- BigQuery는 쿼리 하나를 **수천 대의 머신에 분산 처리**해 결과를 낸다
- 질의는 표준 **SQL**로도, **AI를 이용한 자연어**로도 할 수 있다
- 서버를 운영하지 않으므로 쿼리가 없는 시간에는 서버 비용이 들지 않는다
- 영상의 한 줄 정리: "관리가 필요 없고 한계가 없는 스프레드시트"

---

## 💡 개발자 포인트
- **용도로 나누기**: 트렌드·대시보드·개수·합계·빈도 같은 **집계/분석(OLAP)**은 BigQuery, 앱 트랜잭션과 단건 조회(OLTP)는 관계형 DB
- 앱·로그·매출 데이터는 운영 DB에서 만들어진 뒤 **BigQuery로 흘려보내 분석**하는 파이프라인 구조를 권장
> 주의: BigQuery는 적은 데이터를 다루거나 특정 레코드 하나를 찾는 앱 백엔드 용도로는 맞지 않는다. 운영 DB를 대체하는 게 아니라 보완하는 도구다
- 쿼리 단위로 과금되므로 쿼리 설계(스캔하는 데이터 양)가 곧 비용 관리 포인트가 된다
- 인프라 운영 부담이 없어 데이터 엔지니어링 리소스가 적은 팀에 특히 맞다
