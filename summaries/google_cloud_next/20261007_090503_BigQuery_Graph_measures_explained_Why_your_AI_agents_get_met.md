# BigQuery Graph measures explained (Why your AI agents get metrics wrong and how measures fix it)

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=CEtOL6yDmMc
- **요약 일시**: 2026-10-07 09:05:03

---

## 🔑 핵심 요약
- 여러 테이블을 **JOIN**하면 1:N 관계 때문에 행이 복제되고, 이를 단순 `SUM`하면 지표가 **조용히 부풀려짐** (fan-out 문제)
- **BigQuery Graph Measures**는 집계 규칙을 쿼리가 아닌 **그래프 정의(데이터 자체)**에 넣어, 엔터티 ID 기준으로 그룹 내 **한 번만 집계**되도록 보장
- `MEASURE(...)`로 정의하고 쿼리에서 `AGG()`로 호출 → AI 에이전트(대화형 분석 에이전트)도 올바른 숫자를 반환

---

## 📣 주요 발표 내용
- **문제 사례**: 음반사 데이터(곡 → 아티스트 → 레이블, 곡 ↔ 플레이리스트)
  - 실제 레이블 총 스트리밍: **51억** 회
  - 플레이리스트 테이블과 JOIN 후 `SUM` 결과: **126억** 회 (약 2.5배 과다 집계)
  - 원인: 'Neon Summer'가 4개 플레이리스트에 포함 → 20억이 4번 더해져 80억으로 계산
  - 쿼리는 **오류 없이 실행**되므로 대규모 실데이터에선 발견이 거의 불가능
- **Graph Measures 구성 3단계**
  1. BigQuery에 있는 기존 테이블에 접근
  2. **Property Graph**로 테이블 간 관계 정의 (데이터 복사·이동 없음, SQL 직접 작성 또는 콘솔 **시각적 편집기** 사용)
  3. 그래프 노드에 **Measure** 추가 (예: 곡 노드에 스트리밍 합계)
- **정의 방법**: 그래프 정의의 곡(Song) 테이블 속성 목록에 `MEASURE(SUM(streams)) AS total_streams` 형태로 추가
  - 레이블 노드도 `label_id` 기준으로 레이블 예산 등 동일 방식 적용 가능
- **쿼리 방법**: 원시 컬럼 `SUM(streams)` 대신 `AGG(total_streams)` 호출
  - 같은 매치 데이터에서 `SUM` → 126억, `AGG` → **51억** (정확)
- **재사용성**: GROUP BY 기준을 레이블 → 플레이리스트로 바꿔도 `AGG` 표현식은 그대로 유지, 각 곡은 플레이리스트 내에서 한 번씩만 집계
- **경로 기반 심층 분석**: 레이블 → 아티스트 → 곡 → 플레이리스트 경로를 따라가면
  - 51억 중 **47억(92%)**이 'Hot Right Now' 단일 플레이리스트 노드를 경유 → 총합만으로는 보이지 않는 **노출 집중 리스크** 파악
- **연동 생태계**
  - 콘솔 시각화 편집기 / **Data Agent Kit**(원하는 IDE에서 사용)로 그래프 생성
  - 생성된 그래프는 **Knowledge Catalog**에 노출되어 조직 내 검색 가능
  - **대화형 분석 에이전트(Conversational Analytics Agent)**가 그래프와 직접 상호작용 → 별도 어시스턴트 구축 불필요

## 💡 개발자 포인트
> ⚠️ **JOIN 후 SUM은 침묵하는 버그**: 1:N / N:M 관계 테이블을 조인한 뒤 상위 엔터티의 수치 컬럼을 그대로 `SUM`하면 중복 집계됩니다. 에러가 나지 않으니 텍스트-투-SQL 에이전트가 생성한 쿼리에서 특히 위험합니다.

- 집계 규칙("곡당 스트리밍은 한 번만")을 **모든 쿼리 작성자/에이전트가 기억하게 하지 말고** 그래프 정의의 `MEASURE`로 중앙화할 것
- Measure는 노드의 **키(ID)**에 묶여 있으므로, 여러 경로로 같은 노드가 매칭돼도 그룹 내 dedupe가 자동 보장됨
- 쿼리 패턴 변경 요약

| 구분 | 기존 방식 | Graph Measures |
| --- | --- | --- |
| 정의 위치 | 쿼리마다 직접 | 그래프 정의 내 `MEASURE(...)` |
| 쿼리 호출 | `SUM(streams)` | `AGG(total_streams)` |
| 중복 집계 | 발생 (126억) | 방지 (51억) |
| GROUP BY 변경 시 | 로직 재작성 필요 | 표현식 그대로 재사용 |

- LLM 기반 분석 에이전트를 붙인다면 **시맨틱 레이어로서 Property Graph + Measures**를 먼저 설계하는 것이 숫자 신뢰도를 높이는 지름길
- 총합 지표 외에도 그래프 **경로(path)**를 유지해 의존도·집중도(single point of failure) 분석에 활용 가능
