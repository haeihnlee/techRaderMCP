## 🔑 핵심 요약
- AI 앱 아키텍처는 **단일 에이전트**, **에이전트 팀**, **그래프 워크플로** 세 가지 패턴으로 나눌 수 있음
- 단일 에이전트는 **유연성**, 에이전트 팀은 **책임 분리**, 그래프 워크플로는 **구조와 신뢰성**을 줌
- 세 패턴은 함께 쓸 수 있으며, 앱이 실제로 해야 하는 일을 기준으로 골라야 함

## 📣 주요 발표 내용
- 예시 시나리오: 고객 서비스 앱에서 "상품이 안 왔어요, 환불되나요?" 요청 처리
- **단일 에이전트**: 모델 + 업무 지침 + 도구(`주문 조회`, `배송 추적`, `환불 정책 검색`, `환불 요청`)를 **루프**로 실행
  - 모델이 도구 호출을 요청 → 앱이 실행 후 결과 반환 → 모델이 다음 행동 결정
  - 배송 중이면 예정일 안내, 주문을 못 찾으면 추가 정보 요청처럼 상황에 맞춰 대응
  - 실행 횟수 등에 **제한**을 걸어 막혔을 때 멈추거나 도움을 요청하도록 설정 가능
- **에이전트 팀**: 부모 에이전트(**코디네이터**)가 요청을 받아 전문 하위 에이전트에게 위임
  - 배송 에이전트: 배송 조회·업데이트 도구
  - 결제 에이전트: 결제·환불 이력·환불 정책 검토 도구
  - 모든 에이전트가 같은 기본 모델을 써도 됨. 역할 차이는 **지침·도구·컨텍스트**에서 나옴
- **그래프 워크플로**: 앱의 단계(**노드**)와 연결(**에지**)을 정의한 "실행 가능한 순서도"
  - 에지로 다음 단계, 병렬 실행, 분기, 이전 단계로 되돌아가기(루프)를 정의
  - 노드 하나는 일반 함수, 모델 호출, 에이전트, 에이전트 팀, 하위 워크플로 중 무엇이든 될 수 있음
- 워크플로 예시 흐름
  1. 일반 코드: 주문·결제 기록을 불러오고 로그인한 고객의 주문인지 확인 (모델 없음)
  2. 에이전트 팀: 배송·결제 조사 후 해결 방안 제시 (예: 분실로 인한 환불 권장)
  3. 코드 검사: 환불 조건 확인, 중복 요청 검사, 환불 가능 금액 계산
  4. 분기: 통과 → 환불 함수 호출 / 정책 예외 → 담당자에게 전달 / 정보 누락 → 고객에게 묻고 조사 단계로 루프
  5. 응답 작성: 확인된 결과를 바탕으로 **모델 1회 호출**로 고객 응답 생성

## 💡 개발자 포인트
- 처음에는 **단일 에이전트 + 집중된 도구 세트 + 한 곳에서 관리하는 지침**으로 시작하는 것을 권장
- 도구·정책·책임(배송, 결제 분쟁, 반품, 구독 변경 등)이 많아지면 에이전트 팀으로 나누기
> ⚠️ 에이전트 팀의 대가는 **조정 비용**임. 에이전트 사이에 넘기는 과정에서 세부 정보가 빠지면 잘못된 결정으로 이어지고, 에이전트가 늘어날수록 **비용과 지연**도 커짐
- 금액 계산이나 소유권 확인처럼 **정확해야 하는 검사는 모델이 아니라 코드**로 처리
> ⚠️ 검사 함수를 에이전트 **도구**로 두면 모델이 도구를 골라야 하므로 토큰 비용이 들고 신뢰성이 떨어짐. 반드시 거쳐야 하는 검사는 워크플로 **노드**로 만들어 순서와 실행을 보장할 것
- 환불 같은 민감한 함수는 어떤 아키텍처에서든 **함수 내부에서 자체 규칙(허용 여부)을 검증**하도록 구현
- "결제 서비스가 성공을 보고한 뒤에만 고객에게 확인 메시지 전송", "일부 결과는 사람이 검토" 같은 프로세스 요구사항은 워크플로로 명시
- 꼭 단일 에이전트 → 팀 → 워크플로 순서로 갈 필요는 없음. 비즈니스 규칙이 명확한 프로세스라면 처음부터 워크플로로 시작하는 편이 유리할 수 있음
- 선택 기준 정리

| 패턴 | 얻는 것 | 적합한 경우 |
| --- | --- | --- |
| 단일 에이전트 | 유연성, 단순함 | 단순한 업무, 목표 중심의 탐색 |
| 에이전트 팀 | 책임 분리, 지침 관리 용이 | 도메인·도구·정책이 많아질 때 |
| 그래프 워크플로 | 구조, 신뢰성, 명시적 제어 | 필수 단계·여러 경로·사람 검토가 있을 때 |
