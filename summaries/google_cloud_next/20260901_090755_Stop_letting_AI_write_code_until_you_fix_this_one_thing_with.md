## 🔑 핵심 요약
- **코드 작성 자동화**보다 어려운 문제는 코드 리뷰·배포·운영·장애 대응까지 포함한 전체 **SDLC**를 자동화하는 것이다.
- 프로덕션에서 올바른 해결책을 고르려면 코드베이스만이 아니라 조직의 관례, 서비스 구조, 과거 장애 이력 같은 **운영 컨텍스트**와 인간의 판단이 필요하다.
- `Antigravity`와 **Cleric**을 결합하면 코딩 에이전트가 Kubernetes 로그와 프로덕션 지식을 활용해 장애를 분석하고, 사후 대응뿐 아니라 배포 전 잠재 문제까지 선제적으로 찾을 수 있다.

---

## 📣 주요 발표 내용
- **소프트웨어 엔지니어링의 목표 재정의**
  - AI는 소프트웨어 엔지니어링의 기본 원리를 바꾼 것이 아니라, 고객 가치를 전달하기까지의 수작업과 중간 단계를 빠르게 만들었다.
  - 코드를 누구나 빠르게 생성할 수 있게 되면서 병목은 작성이 아니라 **무엇을 올바르게 만들고 운영할지 판단하는 일**로 이동했다.
- **Cleric의 지속 학습형 SRE 에이전트**
  - 프로덕션 환경을 백그라운드에서 스캔하며 인프라·관측성·도메인 정보를 지식 베이스로 축적한다.
  - SRE와 개발자가 나눈 대화와 과거 장애·해결 사례도 검색 가능한 운영 컨텍스트로 활용한다.
- **`Antigravity` 기반 장애 분석 데모**
  - 에이전트가 Kubernetes 컨텍스트를 전환하고 특정 네임스페이스의 최근 30분 로그를 병렬로 조회한다.
  - 로그 플러딩, 상품 누락, Prometheus 스크래핑 문제 등 상위 이슈를 요약한 뒤, 선택한 이슈의 원인과 조치 방향을 추가로 조사한다.
- **Cleric MCP 연동**
  - `Antigravity`가 Cleric의 MCP를 통해 운영 지식 베이스와 과거 이슈를 검색한다.
  - 상품 누락이 정상적인 판매 종료인지, 일시적 로딩 문제인지, 핵심 상품 삭제라는 심각한 장애인지 구분할 수 있도록 맥락을 보강한다.
- **사후 대응에서 사전 예방으로 확장**
  - 장애가 발생한 뒤 깨우는 reactive 문제 해결을 넘어, 변경 사항을 배포한 직후 문제가 되기 전에 에이전트가 잠재적인 실패를 찾아 수정하도록 한다.

## 💡 개발자 포인트
- 코드 에이전트에 저장소 파일만 제공하면 가능한 구현 방식은 많지만, 조직의 서비스 소유권·변경 관례·운영 제약을 몰라 잘못된 해결책을 선택할 수 있다.
- 프로덕션 자동화의 핵심은 단순한 로그 요약이 아니라 **운영 판단에 필요한 맥락을 에이전트가 지속적으로 학습하고 검색하는 구조**다.
- 에이전트를 실제 운영 환경에 연결할 때는 Kubernetes 컨텍스트, 로그 범위, 관측성 데이터, 과거 장애 기록의 접근 권한을 최소화하고 감사 가능하게 관리해야 한다.
- > AI가 생성한 코드를 바로 배포하는 것보다, 해당 변경이 고객과 운영 시스템에 미칠 영향을 검토하는 **판단 단계**를 자동화·보강하는 것이 중요하다.
- > 운영 에이전트는 장애를 스스로 수정하도록 하기 전에 읽기 전용 분석, 승인 기반 변경, 롤백 경로를 분리해 점진적으로 도입해야 한다.
- 개발자는 반복적인 온콜·인프라 조사보다 고객 문제 정의, 우선순위 결정, 시스템 설계와 같은 고차원적인 판단에 더 많은 시간을 쓸 수 있다.
