# The post build interrogation method: No code bug finding

- **컨퍼런스**: Google Cloud Next
- **출처**: https://www.youtube.com/watch?v=a8RaOENF34M
- **요약 일시**: 2026-11-25 09:04:26

---

## 🔑 핵심 요약
- **빌드 후 점검(Post-build Interrogation)**: 앱이 완성된 뒤 코드를 보지 않고 에이전트(Gemini)에게 질문을 계속 던져서 숨은 가정과 예외 상황을 찾아내는 방법
- `grill me`처럼 에이전트가 사용자에게 캐묻게 하는 방식과 반대로, **개발자가 에이전트에게 캐묻는** 방식
- 대화에서 나온 내용은 **아티팩트**(데이터 흐름 문서와 이슈 목록)로 남기고, 실제 수정은 별도 세션에서 **계획 모드(Plan Mode)**로 진행

---

## 📣 주요 발표 내용
- 시리즈 "Build It"에서 만들어 온 **Smart Personal Trainer** 앱(로컬 DB와 Firebase/Firestore 동기화 구조)을 예제로 시연
- 사용 도구는 **Google Antigravity**이며, 대화마다 개별 태그를 붙여 나중에 분석���고 돌아볼 수 있음
- 첫 프롬프트에서 에이전트 동작을 맞춤 설정함
  - "코드는 몰라도 된다고 가정하고, 시스템 아키텍트 관점에서 개념만 설명해 줘"
  - "한 번에 다 말하지 말고 단계별로 나눠서, 장황하지 않게 설명해 줘"
- 질문 흐름: "저장 요청이 실패하면 어떻게 되나?" → "우리 앱은 그걸 어떻게 감지하나?" → "보류 중인 발신함은 별도 DB인가?"
- Gemini가 **트랜잭션 원장 패턴**과 **스냅샷(diff push) 패턴**을 섞어서 설명하는 모순을 발견하고, 두 방식 중 어느 쪽이 우선하는지 다시 질문함
- 그 결과 **데이터마다 단일 정보 소스(SSOT)가 다르다**는 점이 드러남

| 데이터 종류 | 단일 정보 소스 |
| --- | --- |
| 활성 운동 계획, 채팅 | 로컬 DB |
| 세션 로그, 개인 기록 등 과거 데이터 | 클라우드(Firestore) |

- **발견한 예외 상황**: 지하 헬스장처럼 완전히 오프라인인 상태에서 운동을 끝내면 '오늘' 화면에는 완료로 표시되지만, 동기화가 재시도되기 전까지는 '기록' 탭(클라우드)에 세션이 나타나지 않음

> ⚠️ 주의: 에이전트가 만든 앱이 잘 돌아가는 것처럼 보여도, 스펙에 없던 부분은 에이전트가 **임의로 가정하고 구현**했을 수 있음. 그 가정이 맞는지 직접 확인해야 함

## 💡 개발자 포인트
- 에이전트의 답이 모순되면 환각이라고 단정하지 말고 **맥락을 보충해서 다시 질문**하기. 질문을 잘못 이해했을 가능성이 큼
- "왜 이렇게 설계했어?"와 "이 예외 상황도 처리해야 할까?"처럼 **질문 형태로 의견을 내면** 설계 근거를 명확하게 확인할 수 있음
- 문제를 찾은 그 자리에서 바로 고치지 않는 이유
  - 몰입 상태가 깨짐
  - 에이전트의 컨텍스트가 섞여 원래 작업으로 돌아가기 어려워짐
- 대신 **아티팩트 2개를 만들어 달라고 요청**하기
  - **데이터 흐름 문서**: 우리 앱에서 실제로 논의한 내용만 정리(고수준 아키텍처, 동기화 모델, 데이터 흐름, 오류 처리). 대화가 이어질 때마다 계속 업데이트
  - **이슈 목록**: 다른 에이전트가 읽고 바로 고칠 수 있을 만큼 자세하게 작성
- 이 아티팩트를 새 세션의 컨텍스트로 넘기면 에이전트가 코드베이스 전체를 다시 조사할 필요가 없어 **토큰을 아낄 수 있고**, 팀원이나 다른 에이전트가 온보딩할 때도 쓸 수 있음
- 복잡한 이슈는 **계획 모드**로 해결 계획 문서를 따로 만들어 이슈에 연결하기
  - 해결안 아이디어를 여러 개 놓고 에이전트와 토론함
  - 예: 아이디어 3개를 제시하자 에이전트가 하이브리드 방식을 제안함
- 오프라인 우선(Offline-first) 앱이라면 **로컬과 클라우드가 충돌할 때 어느 쪽을 우선할지**와 **재시도/동기화 정책**을 데이터 종류별로 명시해야 함
