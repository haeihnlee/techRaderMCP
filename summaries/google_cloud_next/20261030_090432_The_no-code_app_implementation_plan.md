## 🔑 핵심 요약
- **Build It** 시리즈 에피소드: 맞춤형 AI 개인 트레이너 앱을 **사양 중심 구축(spec-driven building)** 방식으로 만들면서, 코드를 쓰기 전 마지막 단계인 **구현 계획(implementation plan)** 을 세우는 과정
- `Antigravity` + `Gemini` 에이전트에게 지시 대신 **질문**을 던져 사양 문서의 누락 정보와 문서 간 모순을 먼저 찾아냄
- 결과물: 보강된 설계 문서 3개 + 구현 계획 1개(`docs/architecture` 디렉터리), **단계별 마일스톤 + 자체 검증** 방식에 버전 관리까지 포함

---

## 📣 주요 발표 내용
- **계획 단계에서는 빌드 금지**: "아무것도 만들지 마, 구축하지 마, 코드도 쓰지 마"를 프롬프트에 분명히 적어 에이전트를 검토 작업에만 묶어 둠
- **두 가지 사전 질문**: ① 추가로 줘야 할 정보는 무엇인가 ② 설계 문서 3개 사이에 모순은 없는가 → 에이전트가 누락 항목과 모순 목록을 만들어 줌
- **가정 vs 권장 비교 기법**: "이 문서대로 앱을 만들었다면 각 질문에 어떤 답을 **가정**했을까? 그리고 무엇을 **권장**하나?"라고 물어 둘의 차이와 권장안의 이점을 요약받음
- **문서는 제자리에서 수정**: 별도의 "가정 문서"를 추가하지 않고 기존 문서를 직접 고침 — 에이전트는 문서를 순서대로 읽기 때문에 다른 파일에 있는 세부 내용은 놓치기 쉬움
- **백업 → 수정 → 검토 → 백업 삭제**: 설계 문서 정도는 Git 없이 Gemini에게 백업본을 만들게 하고, 수정 전에 구현 계획(변경 내역)부터 쓰게 한 뒤 결과를 검토하고 백업을 지움
- **새 세션으로 분리**: 작업 성격이 바뀌면 같은 워크스페이스 안에서 새 세션을 열어 에이전트 컨텍스트가 섞이지 않게 함
- **문서 3개는 합치지 않음**: 에이전트는 컨텍스트를 청크 단위로 탐색하므로, 큰 문서 하나로 합치면 attention이 흩어짐 → 따로 두는 게 정보 찾기에 유리
- **구현 계획 문서는 따로 둠**: 설계 문서를 바탕으로 "실제로 어떻게 구현할지"를 명시하는 별도 문서 작성
- **4개의 전략적 관문(Gate)** 을 둔 단계별 마일스톤 방식 (아래 표 참고), 각 관문마다 사람이 확인하는 단계 포함
- 마지막으로 **버전 관리**를 구현 계획에 넣음 — 2단계에서 깨지면 1단계 체크포인트로 롤백할 수 있게

---

## 💡 개발자 포인트
- 에이전트에게는 **진술보다 질문**으로 물어볼 것 — 진술형 프롬프트는 원하는 답을 유도하게 되고, 질문형이어야 모델이 스스로 판단함 (LLM 내부 동작을 이해하는 데도 도움)
- 코드 생성 전에 **누락 정보·모순 점검**을 따로 돌리기: 사람이 답할 수 있는 문제를 에이전트가 **추측하지 않도록** 하는 게 핵심
- 문서 구조는 **attention 관점**으로 설계: 관련 내용은 한 문서 안에 논리적 순서로 모으고, 관심사가 다른 문서는 따로 둠
- 한 번에 "앱 다 만들어 줘"는 피할 것 — 나중에 문제가 생기면 어디서 깨졌는지 찾기 매우 어려움
- `Antigravity` 는 브라우저에서 앱을 직접 실행해 기능을 테스트하고 **스스로 수정**할 수 있음 → 그래도 관문마다 사람이 확인하는 단계는 남겨 두기
- 단계별 체크포인트에 맞춰 **버전 관리 전략**을 계획에 미리 넣어 두면 롤백이 쉬움

> 주의: 설계 문서를 제자리에서 수정하면 되돌리기 까다로울 수 있으므로, 수정 전에 반드시 백업(또는 VCS 커밋)을 남길 것

| 관문 | 범위 | 사람의 확인 항목 |
| --- | --- | --- |
| Gate 1 | 기반 구축, 표준 타입 정의, 데이터베이스 | 타입 검사, DB·에뮬레이터 시드가 오류 없이 생성되는지 |
| Gate 2 | 서버 API·엔드포인트, AI 코치 엔진(백엔드/두뇌) | 백엔드 로직이 제대로 동작하는지 |
| Gate 3 | 상태 인프라, 짐 플로어(gym floor) 실행 환경 | 실행 흐름 검증 |
| Gate 4 | 뷰 조립, 다듬기, 체계적 시스템 테스트 | 전체 시스템 검증 |
