## 🔑 핵심 요약
- 'Build it' 시리즈 2편: AI Studio로 만든 **AI 개인 트레이너** 프로토타입을 버리고, 실서비스 수준으로 다시 만들기 위해 **시스템 설계 문서(데이터 아키텍처 스펙)** 를 코드 없이 작성한다
- **Google Antigravity** 에서 기획 동반자 에이전트(POC)와 대화하며 **Cloud Firestore** 데이터 구조, 엔드포인트, 메모리 구조를 설계한다
- 핵심 교훈은 **언제 AI를 쓰고 언제 쓰지 말지** 정하는 것: 운동 라이브러리는 미리 만들어 두고, AI는 조합만 맡겨 지연 시간과 토큰 비용을 줄인다

---

## 📣 주요 발표 내용
- **Antigravity 에이전트/스킬 생성**: 별도 설정 없이 자연어로 요청하면 에이전트가 만들어지고, 메인 에이전트는 질문을 던지고 비판하는 **기획 파트너** 역할만 맡는다
- **하이브리드 설계 (AI 생성 + 라이브러리 조회)**: 운동 설명은 미리 정의한 `exercises` 최상위 컬렉션에 두고, 에이전트는 운동을 골라 계획으로 묶기만 한다
- **운동 블록 구조**: 블록 안에 운동 리스트를 두는 형태이고, `type` 필드(단일 세트/슈퍼세트)는 **삭제**했다. 리스트 길이로 알 수 있기 때문이다
- **주간 계획 저장 방식 비교**: 한 주를 문서 하나에 넣는 '스파이럴 노트북' 방식과 `workouts` 하위 컬렉션으로 나누는 '파일 캐비닛' 방식을 비교한 끝에 **스파이럴 노트북**을 골랐다
- **주 번호 대신 날짜 기반**: '3주 차' 같은 번호 대신 특정 날짜 기준으로 주를 식별한다
- **수정 제안 칩 미리 생성**: 주간/운동 뷰에 뜨는 수정 제안 칩은 계획을 생성할 때 같이 만들어 저장한다
- **엔드포인트 2개로 분리**: **주간 전체 생성**과 **하루치 빠른 수정**은 목표와 지연 시간 요구가 다르므로 따로 둔다
- **Tool calling**: 에이전트에 **도구 레지스트리**를 주고, 단순 답변/하루 수정/주간 재생성 중 무엇을 할지 에이전트가 직접 고르게 한다
- **인라인 카드 + 수락 흐름**: 에이전트가 수정한 계획을 채팅 안에 카드로 보여 주고, 사용자가 **수락**을 눌러야 Firestore에 반영한다 (사람이 개입하는 구조)
- **주간 채팅 버킷**: 메시지마다 문서를 만드는 방식과 채팅 전체를 문서 하나에 넣는 방식의 중간으로, **주 단위 채팅 문서**를 쓴다
- **운동 기록**: 완료한 세션은 각각 별도의 영구 문서로 저장한다
- **온보딩 마법사 없음**: '나에 대해 알려 주세요' 채팅에서 사용자가 자유롭게 말하면 에이전트가 목표를 파악해 첫 주 계획을 만든다
- **계층형 메모리**: 1단계는 영구 선호(예: 주 2회 이상 달리기), 2단계는 생리적·상황적 정보(예: 햄스트링 통증, 대회 준비)이고, 각 항목은 `category`·`fact`·`source` 로 저장한다
- **자율 메모리 관리**: 대화 중에 에이전트가 프로필을 실시간으로 수정하고 다듬을 권한을 가진다 (쌓기만 하는 메모리가 아님)

## 💡 개발자 포인트
- 자주 바뀌지 않는 비싼 콘텐츠(운동 설명, 영상, 자세 팁)는 **미리 만들어 두고**, LLM은 조합·선택만 하게 해서 응답 시간을 줄이고 결과의 일관성을 지킨다
- **이미 가진 데이터로 알 수 있는 값은 저장하지 않는다**: `type`, `status`, 계획 제목처럼 클라이언트가 계산할 수 있는 필드는 지운다
- Firestore 문서 설계는 **읽기 횟수와 문서 크기 제한 사이의 트레이드오프**다. 데이터가 작고 한 번에 같이 읽히면 문서 하나로 합친다
- 생성 요청과 수정 요청은 **반환하는 데이터 형태와 지연 시간 요구가 다르므로** 엔드포인트를 나눈다. 하루치 수정에 주간 전체를 다시 만들지 않는다
- 하나의 채팅 엔드포인트에서 여러 동작을 처리하려면 프롬프트 분기 대신 **tool calling** 으로 에이전트가 고르게 한다
- AI 출력을 바로 DB에 쓰지 말고 **사용자 수락 후 반영**해서 의도치 않은 덮어쓰기를 막는다. 클라이언트는 DB와 동기화해 항상 최신 상태를 보여 준다
- 채팅 저장은 앱의 주 단위 뷰에 맞춰 **주간 버킷**으로 묶어서 클라이언트가 문서를 여러 번 가져오지 않게 한다
- 에이전트 메모리는 **영구 정보와 일시적 정보로 계층**을 나누고, 오래되거나 틀린 정보를 **고치거나 지우는** 경로까지 설계한다
- 바이브 코딩 프로토타입은 구조를 파악하는 데만 쓰고, 실제 버전은 **스펙 문서를 먼저 확정한 뒤** 처음부터 다시 만든다

> 주의: 예시로 든 'AI 생성 지연 15초 → 라이브러리 조합 2초' 수치는 대화 중 에이전트가 낸 추정치이며 실측 벤치마크가 아님
