## 🔑 핵심 요약
- **Claude Opus 5**는 기존 Opus 4.8 프롬프트로도 잘 동작하지만, **응답이 길어지고 자기 검증·서브에이전트 위임을 스스로 더 많이 한다**는 점이 튜닝 포인트다
- 기존 프롬프트의 **"검증 단계를 추가하라", "재확인하라" 지시는 삭제**해야 한다 — 모델이 이미 하는 일과 겹쳐 토큰만 낭비된다
- `effort`를 **`low`/`medium`으로 적극 내려쓰는 것**이 비용·지연 제어의 주 수단이며, 어려운 코딩·에이전틱 작업만 `xhigh`로 올린다

---

## 📣 주요 발표 내용

**Opus 4.8 대비 개선점**

- **에이전틱 코딩** — 다중 파일 기능, 대규모 리팩터링, 종단간 기능 작업에 가장 강하다. 스텁·플레이스홀더를 남기지 않고 작업을 끝까지 완료하며, **전체 명세를 미리 주고 자율 실행시킬 때** 성능이 가장 좋다
- **코드 리뷰·버그 탐지** — 정밀도와 재현율이 모두 높다. 낮은 `effort`에서도 정확도가 유지되어 리뷰 시점 빠른 패스 + 이후 정밀 패스 구성이 가능하다
- **낮은 effort 효율** — `low`/`medium`이 상위 설정 대비 훨씬 적은 토큰·지연으로 높은 품질을 낸다
- **비전** — 차트·문서·다이어그램 이해, UI/프론트엔드 시각적 복제에 강하다. 도구로 반복 분석·크롭·시각 검증하게 할 때 가장 강하며, **thinking보다 도구 사용이 비용 효율적**이다
- **롱컨텍스트** — **1M 토큰**이 기본값이자 최대값이며, 창 전체에서 지시 준수·도구 호출·추론이 일관되다
- **오피스·문서** — 복잡한 다중 시트 스프레드시트(비자명한 수식 포함), 구조화된 슬라이드 덱 생성
- **멀티 에이전트 조율** — 서브에이전트 팀을 잘 조율하고 writer-verifier 패턴이 효과적, 에이전트 간 작업 덮어쓰기가 드물다

**동작 변화와 대응 프롬프트**

| 변화 | 대응 |
|---|---|
| 사용자 응답이 이전 Opus보다 길다 | 간결성 지시를 명시. `effort`는 **thinking 양**을 조절하며 가시 응답 길이는 확실히 줄이지 못한다 |
| 에이전틱 작업 중 진행 상황을 많이 서술 | 원하는 **주기와 형태를 서술** (첫 도구 호출 전 한 문장, 중요 발견 시만 업데이트, 완료 시 결과부터) |
| 디스크에 쓰는 문서(리포트·MD)가 길다 | 길이 캘리브레이션 명시 — "필러 섹션·중복 요약·보일러플레이트로 늘리지 말 것" |
| 작업 범위를 스스로 확장 | 범위를 명시적으로 제약 |
| 서브에이전트에 더 적극 위임 | 위임 시나리오를 명시하거나 **결정적 상한**을 설정 |
| 이전 발언 정정을 많이 서술 | "사용자의 코드·결론·결정을 바꿀 오류만 정정"으로 제한 |

## 💡 개발자 포인트

**즉시 제거해야 할 프롬프트 (비용만 늘고 품질 이득 없음)**

> `"모든 비자명한 작업에 최종 검증 단계를 포함하라"`, `"서브에이전트로 검증하라"`, `"답을 다시 확인하라"`, `"응답 전 재검증하라"` — Opus 5는 **지시 없이도 자기 검증·자기 수정을 수행**한다. 이런 지시는 모델 자체 동작과 겹쳐 **과잉 검증**을 유발한다. 레거시 하네스의 별도 검증 스캐폴딩도 동일하다.

**코드 리뷰 프롬프트의 함정**

> 리뷰 프롬프트에 `"높은 심각도만 보고하라"` 또는 `"보수적으로 판단하라"`가 있으면 모델이 **문자 그대로 따라 보고량이 줄어든다**. 전부 보고하게 하고 **별도 패스에서 필터링**하는 구조로 바꿀 것.

**effort 재점검 필요**

> 이전 모델에서 `effort` 기본값을 그대로 가져왔다면 **자체 eval로 effort 스윕을 다시 돌려야 한다**. 기본값 `high`에서 시작해 품질이 유지되는 구간까지 내리는 것이 권장 경로다.

- 비전 관련 프롬프트 우회책도 재검증 대상 — 이전 모델용으로 튜닝한 workaround가 더는 불필요할 수 있다
- 비용 민감 워크로드는 위임에 상한을 걸 것. 위임은 **진짜 독립적이고 규모 있는 작업**에서만 이득이며, 작은 작업엔 비용·시간이 배가된다

**thinking 비활성화 시 두 가지 아티팩트 (주의)**

> **1) 도구 호출이 텍스트로 유출** — 구조화된 `tool_use` 블록 대신 사용자 텍스트에 도구 호출을 써버린다. 턴은 정상 종료되지만 **호출은 실행되지 않으며**, 에이전틱 루프에서는 유출된 텍스트가 대화 히스토리에 남아 이후 턴까지 오염시킨다. 검색 등 도구 중심 워크로드에서 가장 흔하다.
>
> **2) 내부 XML 태그 유출** — `<thinking>` 등 내부 태그가 가시 응답에 섞인다. 시스템 프롬프트에 **"생각하지 말라", "추론하지 말라" 류의 규칙이 있으면 제거**해야 한다 — 오히려 태그 유출을 늘린다.

- **1차 완화책은 thinking을 켜 둔 채 낮은 effort로 비용을 제어하는 것**이다. 대부분의 작업에서 **thinking 활성 + `low` effort**가 유사 비용의 thinking 비활성보다 성능이 좋다
- thinking 비활성이 불가피한 통합에는 단일 통합 지시가 두 아티팩트를 동시에 완화한다: 도구 호출 전 발화 허용 + 맞는 도구가 없을 때의 대안 제시 + 내부 태그 금지
- 태그를 **이름으로 지목하는 지시는 효과가 떨어진다** — 일반형 표현을 쓸 것

## 📅 버전 / 출시 일정

| 항목 | 값 |
|---|---|
| 대상 모델 | Claude Opus 5 |
| 비교 기준 | Claude Opus 4.8 |
| 컨텍스트 윈도우 | 1M 토큰 (기본값 = 최대값) |
| thinking 기본 | **활성** (Opus 4.8과 달라진 지점) |
| thinking 비활성 조건 | `effort` **`high` 이하**에서만 가능 |
| effort 기본값 | `high` |
| 권장 effort | `low`/`medium` 적극 활용, 고난도 작업은 `xhigh` |

> 마이그레이션 시 API 변경사항(thinking 기본 활성, 비활성화 시 `high` 상한)은 공식 마이그레이션 가이드 참조.
